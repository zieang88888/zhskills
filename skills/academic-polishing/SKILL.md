# 专业文稿润色 · academic-polishing

> **二次开发**：本技能改编自 [Yuan1z0825/nature-skills](https://github.com/Yuan1z0825/nature-skills) 的 nature-polishing（Apache-2.0 © 原项目所有者 Yuan1z0825），在保留其四轴路由（文献类型×章节×语言×目标期刊）与「先内容后语言、证据边界不越界」核心方法论基础上，平移到中文专业文稿场景并升级为「提示词 + 可执行 CLI」双形态。署名见本目录 `NOTICE.md` 与仓库 `THIRD_PARTY_NOTICES.md`。

## 这个技能做什么

把一份已经写好的专业文稿，按**类型 × 章节 × 语言 × 目标场合**四个轴路由，做结构化润色。与普通"改文字"不同，本技能强制**先内容、后语言**：

- **第一轮（内容与结构）**：只动主张与证据的对应、章节结构是否符合该文体惯例、术语是否一致、段落逻辑衔接；**这一轮不许只换漂亮句式而不动结构**。
- **第二轮（语言细节）**：结构定稿后，才动句式、用词、标点、语气分寸。

保留自原项目的四条核心检查（全部沿用）：

1. **内容层检查**：每个主张后面是否有支撑（数据、引文、案例、推导）；数据是否可追溯（来源、口径、时间点）；没有支撑的主张要么补证据、要么降级表述，不许靠修饰把它"擦亮"过去。
2. **结构层检查**：章节顺序、篇幅分配、详略是否符合该文体（论文/技术报告/方案/制度/申报材料）的惯例；典型结构问题（结论前置缺失、结果与讨论重复、措施与问题不对应）优先修。
3. **语言层检查**：术语全文统一；句式服务于逻辑（主从关系、因果方向）；用词与目标场合的正式度匹配。
4. **证据边界检查**：逐句区分**事实 / 推断 / 建议**三类表述——事实（有出处的观察或数据）不得写成推断语气，推断不得写成事实，建议不得伪装成结论；模态词（"表明/提示/可能/应当"）与证据强度匹配。

一句话：**结构不对就先修结构；证据不够就降级或标注；结构证据都稳了，最后才磨句子。**

典型适用场景：论文/课题润色、技术方案打磨、制度文件规范、申报材料自查、对外技术文档定稿。

## 输入要求

- **必填**：待润色的中文专业文稿全文（直接粘贴，或 `.txt` / `.md` 文件）。
- **可选（四轴取值）**：
  - **类型（`--type`）**：论文 / 技术报告 / 方案 / 制度 / 申报材料；默认技术报告。类型决定章节结构惯例与详略标准。
  - **章节**：通常由文稿自身结构识别（摘要/引言/背景/方法/结果/讨论/结论/措施/附则等）；用户点明只润某一章时，按该章惯例处理。
  - **语言（`--lang`）**：zh / en；默认 zh。
  - **目标场合（`--target`）**：如"项目评审""期刊投稿""内部存档""上级汇报"；决定语气分寸、详略与保留口径。
- 结构问题若不补写内容就修不了 → **标（待确认）并在证据边界检查里说明**，禁止为了让文稿"看起来完整"而虚构数据、引文或结论。

## 输出结构（模板见 `scripts/templates/academic-polishing.template.md`）

输出一份完整的润色稿，自上而下四部分：

1. **润色后全文**（Markdown）：结构与证据已修、语言已磨的成稿；不确定处保留（待确认）标注。
2. **修改说明**：按 **内容层 / 结构层 / 语言层** 三组列出主要改动及理由；无改动的组写"无"。
3. **证据边界检查**：逐条列表——原文表述 / 归类（事实·推断·建议）/ 是否越界（是/否）/ 建议改法。
4. **术语一致性**：全文关键术语清单及其统一后写法；同一概念前后不一的，写明统一成了哪个、为什么。

## 工作流程

1. **读稿定轴**：通读全文，识别类型、章节结构、语言；用户给了 `--type` / `--target` 就采用，没给就按文稿本身判断，并在输出开头用一行注明本次路由取值（供用户纠正）。
2. **先内容后语言**：先按"内容层 → 结构层"过一遍，完成主张—证据对应、章节惯例、术语统一的修改；确认这一层无遗留问题后，才进入语言层打磨句式与标点。
3. **证据边界逐条过**：抽稿中所有断言式句子，逐条归类事实/推断/建议；越界的当场在成稿里降级措辞，并在检查表里登记。
4. **落四件套输出**：成稿 + 修改说明 + 证据边界检查表 + 术语一致性清单，按模板组装。

## 质量规则（必须遵守）

- **先内容后语言**：不允许只改语言不动结构；结构问题未修时，禁止进入句式润色。
- **三类表述显式区分**：事实、推断、建议必须分开措辞，模态词与证据强度匹配；禁止把"相关"写成"因果"、把"可能"写成"已经证明"。
- **不虚构**：缺数据、缺出处、缺推导链时，降级表述或标（待确认），绝不补写原文没有的数字、引文、案例。
- **术语一致**：同一概念全文一个写法；中英术语并存时全文统一取舍。
- **不改变作者原意**：只改表达与结构，不替换立场、不增减结论；作者的核心判断保留。
- **不确定必标注**：拿不准的改动标（待确认），并在修改说明里写明为什么不确定。
- **忠于原数据**：数字、日期、金额、人名、项目名、指标口径原样保留。

## 边界与异常处理

- **与 humanize-writing 的分工**：本技能管**结构与专业规范**（章节惯例、主张—证据对应、证据边界、术语一致性）；humanize-writing 管**自然度**（去 AI 味、去模板腔、让文字读起来像人写的）。两者可串用：**先用本技能把结构、证据、术语定准，再用 humanize-writing 磨自然度**；顺序反了会先把"该降级的推断"磨得很顺、掩盖证据问题。
- 文稿严重残缺（只有提纲、没有正文）→ 先指出缺哪部分，标（待确认），不补写。
- 类型判断拿不准（如"方案"还是"技术报告"）→ 按用户给的 `--type`；用户没给则默认技术报告并在开头注明。
- 目标场合未指定 → 按通用正式书面语处理，不过度拔高宣传腔。
- 排版/版式问题（页面布局、图表位置）不属于本技能范围，提示用户另行处理。

## 与脚本配合

- 批量 / 命令行场景：`scripts/draft_academic_polishing.py`（纯标准库，一条命令跑通）；输入为文稿文本，输出为成稿 Markdown（含上述四部分）。
