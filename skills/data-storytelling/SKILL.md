# 数据叙事报告 · data-storytelling

> **二次开发**：本技能改编自 [wshobson/agents](https://github.com/wshobson/agents) 的 data-storytelling（MIT © 2024 Seth Hobson），在保留其核心方法论基础上，升级为「提示词 + 可执行 CLI」双形态。署名见本目录 `NOTICE.md` 与仓库 `THIRD_PARTY_NOTICES.md`。

## 这个技能做什么

把一堆零散的数字、指标、分析结果，组织成一份**有叙事结构、能推动决策**的汇报报告。核心原则一句话：**先回答"所以呢（so what）"，再摆数字。**

- 不是把数据表念一遍，而是先定**一句话核心信息**——这批数字到底在说什么；
- 再从三种故事框架里选最贴合的一种：**问题-解决方案 / 趋势 / 对比**；
- 然后按框架组织每一页：每页一个结论式小标题，数字只作为证据出现；
- 最后落到洞察与建议，并显式声明哪些数字还不确定。

典型适用场景（中文职场高频）：

- **经营分析会 / 月度·季度数据复盘**：把本月经营数据讲成一个有起因、有转折、有结论的故事；
- **看板解读**：面对一屏 KPI，告诉老板"哪些在变好、哪些要警惕、为什么"；
- **投放效果汇报**：把投放消耗、转化、ROI 讲成"钱花得值不值、下一步怎么调"；
- **市场分析报告**：对比几个方向（如先攻哪个区域），用加权打分矩阵支撑建议；
- **向上汇报 / 投资人材料**：非技术听众也能 30 秒抓住重点。

## 输入要求

- **必填**（也是 CLI 输入文件应包含的内容）：
  1. **数据/指标清单**：数字 + 说明，每条至少写清"指标名 = 数值"，尽量带上变化（环比/同比/对比基准），例如"复购率 41%，环比 +12%"；
  2. **汇报背景**：这份报告讲给谁听（上级 / 平级 / 投资人）、要支撑什么决策、汇报时长或篇幅限制。
- **可选**：
  3. **框架偏好**：用户心里已有倾向（"按趋势讲"或"对比两个方案"）；没有就由技能根据数据形态自动选。
- 信息不足时：先向用户追问补全（尤其是"这批数字要支撑什么决策"），不要凭空编结论；实在补不上的地方标注"（待确认）"。

## 输出结构（模板见 `scripts/templates/data-storytelling.template.md`）

一份完整的数据叙事报告，自上而下固定 7 节：

1. **核心信息**：一句话结论式标题——"主语 + 动作 + 结果"，例如"Q3 复购率回升 12%，主要来自新客首单后的 14 天引导"。这句就是整份报告的"so what"，必须能从给定数据推出来。
2. **故事框架选择**：从「问题-解决方案 / 趋势 / 对比」三种里选一种，并写一句**为什么选它**（例如"数据有明确的前后对比和拐点，适合用趋势框架"）。
3. **数据支撑页**：每条数据写成一行卡片——结论式小标题 + 原始数字 + 变化 + 含义。**一条数据一个小标题**，小标题本身就是结论，不是"复购率分析"这种空标题。
4. **叙事结构**：按所选框架组织成"起承转合"或"开场-展开-结论"，并在数据与结论之间给出**过渡话术示例**（如"顺着这个数字往下挖，我们发现……"）。
5. **洞察与建议**：3–5 条，每条严格按"数据 → 洞察 → 建议"三段写，建议必须可执行。
6. **不确定性声明**：哪些数字样本量小、口径未对齐、外推假设强——必须用"约 / 可能 / 需进一步验证"等措辞显式表达，**禁止绝对断言**。
7. **Do & Don't 自查**：对照下方质量规则逐项打勾核对。

## 工作流程

1. **提炼核心信息（第一步）**：读完所有数据，先用一句话回答"这批数字到底在说什么"。写不出这句话，就先停下来追问用户背景，不要急着排结构。
2. **选故事框架（第二步）**：
   - 数据呈现"出了什么问题 + 怎么解" → 用**问题-解决方案**（背景→问题→洞察→方案→预期收益→行动请求）；
   - 数据呈现"一段时间内怎么变的、拐点在哪" → 用**趋势**（起点→发生了什么变化→对比表→关键洞察→下一步）；
   - 数据呈现"两个/多个选项之间选哪个" → 用**对比**（待决问题→各选项对照→加权打分矩阵→建议）。
3. **组织数据支撑（第三步）**：把每条数据改写成"结论式小标题 + 数字证据"，砍掉所有不支撑核心信息的数字（数据不是越多越好）。
4. **串叙事（第四步）**：按框架把数据页串起来，在每两段之间补一句过渡话术，让听众知道"为什么从这条数字跳到这条结论"。
5. **写洞察与建议（第五步）**：每条都走完"数据→洞察→建议"闭环，建议要带动作，不要写"加强关注"这种空话。
6. **标注不确定性 + 自查（第六步）**：把外推、小样本、口径模糊的数字挑出来显式声明；最后对照 Do & Don't 逐项自检。

## 质量规则（必须遵守）

- **只用用户给的数据，不编数字**：报告里出现的每一个数字都必须来自用户输入；需要举例或外推时，明确标注"（估算，需验证）"。
- **核心信息必须可推出**：那句一句话结论，要能从给定数据里直接看出来，不允许跳因果。
- **一页一个核心信息**：每个数据页只讲一件事；标题写成"主语+动作+结果"的结论句，不写"XX 分析""XX 概览"这种空标题。
- **不确定性必须显式表达**：用"约 / 可能 / 大致 / 需进一步验证"，禁止"必然""一定""绝对"这类断言；区间估算写成"40 万–60 万"。
- **不做数据瀑布**：禁止把 20 个数字平铺上去；每条数字都要配一句"这意味着什么"，否则删掉。
- **不为展示牺牲真实**：数字对自己不利也要照写，可以讲它，但不能藏起来或改口径。
- **结论前置**：核心信息放最前面，方法论和过程放后面。
- **中文职场措辞**：过渡话术、建议条目用中文汇报口吻，不直译英文模板腔。

## 边界与异常处理

- 数据只有一两条、撑不起完整故事 → 直说"数据量不足以支撑完整叙事"，给出最简版（核心信息 + 1 条建议），不硬凑 7 节。
- 用户给了矛盾数字（同一指标两个口径）→ 不擅自选边，在"不确定性声明"里列出两个口径并标注"需对齐口径后再下结论"。
- 用户没说汇报对象 → 默认按"给直属上级做月度复盘"的语气写，并在开头提示可调整。
- 用户指定了框架偏好 → 尊重偏好，即使数据形态更像另一种；只在明显不合适时提示一句。
- 涉及金额、ROI 外推 → 一律给区间（保守 / 乐观），并写明假设条件。
- 听众是非业务方 → 术语加一句白话解释，不堆黑话。

## 与脚本配合

- 批量 / 命令行场景：`scripts/draft_data_storytelling.py`（纯标准库，一条命令跑通）；输入为"数据/指标清单 + 汇报背景"的文本文件，输出为成稿数据叙事报告 Markdown。
- `--framework` 参数可显式指定故事框架（问题-解决方案 / 趋势 / 对比）；不传则由模型根据数据形态自动选择。
- 自定义模板：复制 `scripts/templates/data-storytelling.template.md` 修改后使用。
